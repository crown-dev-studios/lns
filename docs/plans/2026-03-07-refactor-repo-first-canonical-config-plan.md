# refactor: Redesign lns around canonical repo config and sync-driven service discovery

## Overview

`lns` should move from a framework-first, registry-first CLI to a repo-first workflow with canonical local configuration. The steady-state model should be:

1. Repo config defines the normal service setup.
2. `lns init` bootstraps that config from codebase inspection when possible.
3. `lns sync` deterministically compiles repo config into registry and Caddy state.
4. Explicit manual service definition remains available for unusual cases.
5. No silent fallback to `generic` or `9000`.

This is a canonical breaking change. No compatibility layer or migration support should be added.

## Problem Statement / Motivation

The current architecture still treats service registration as a manual CLI workflow and uses framework metadata as the primary model. That creates four problems:

- The source of truth lives in the global registry instead of the repo.
- Normal project ports can be misclassified as overrides or anomalies.
- Framework fallback logic allows incorrect registrations to look successful.
- The user has to pass parameters that should be discoverable or repo-defined.

Recent discussion clarified the intended values:

- A repo-local port such as `5179` is normal project configuration, not an override.
- Caddy config must be resolved before reload, not guessed after the fact.
- Explicit `name + port` configuration must remain possible.
- The redesign should be cleanly breaking rather than compatibility-constrained.

## Research Findings

- CLI entrypoints and command surface live in `cmd/lns/main.go`.

- `lns` currently models services around `framework`, `port`, and optional hostname/container metadata.
- HMR proxy behavior is derived from framework metadata rather than a smaller proxy concept.
- Port assignment falls back to framework-specific ranges and then a generic `9000-9999` sweep.
- `lns add` remains the center of the workflow even after experimental autodetection changes.

## Proposed Solution

### Core Model

Replace the framework-first service model with a repo-first service definition centered on:

- `name`
- `root`
- `port`
- `profile`
- `hostname` (optional)
- `source`
- `status`

Recommended meanings:

- `port`: canonical port for the service in this repo
- `profile`: proxy behavior, initially `hmr` or `standard`
- `source`: `config`, `manual`, or `detected`
- `status`: `resolved` or `unresolved`

`framework` should stop being the primary abstraction. If a descriptive framework field remains at all, it should be secondary metadata, not a driver of fallback behavior.

### Canonical Repo Config

Introduce a first-class repo config file, preferably `lns.json`, with this role:

- defines the normal service setup for the repo
- is read by `lns sync`
- may be initially generated by autodetection
- is the authoritative source for Caddy generation

Example shape:

```json
{
  "services": {
    "web": {
      "root": ".",
      "port": 5179,
      "profile": "hmr"
    },
    "api": {
      "root": "api",
      "port": 8000,
      "profile": "standard"
    }
  }
}
```

Important rule: this file is not an override mechanism. It is the repo's declared reality.

Canonical config decisions:

- `lns.json` is mandatory after `lns init`.
- `lns sync` is strictly read, validate, and compile. It must not silently rewrite `lns.json`.
- Service names come from manifest keys under `services`.
- Manual services and detected services use the same manifest shape.
- `sync` is all-or-nothing. One invalid service blocks the full compile step.

### CLI Workflow

Target command surface:

- `lns init`
- `lns sync`
- `lns status`
- `lns reload`
- `lns start`
- `lns stop`
- `lns doctor`
- `lns service add <name> --port <port>`

Command semantics:

- `lns init`
  - infers project name from cwd by default
  - scans the repo
  - writes `lns.json` if missing
  - writes unresolved stubs when detection is ambiguous

- `lns sync`
  - reads `lns.json`
  - validates config against detectable codebase signals
  - rewrites registry state
  - regenerates project and global Caddy config
  - fails on unresolved services

- `lns service add <name> --port <port>`
  - explicit manual service declaration
  - supports optional `--root`, `--profile`, and `--hostname`

Command removal decisions:

- `lns add` should be removed from the primary command surface.
- `lns suggest` should be removed.
- `lns check` can remain as a low-level utility, but it should not be part of the primary workflow.
- Framework flags should be removed from the normal setup flow.

### Detection Role

Autodetection remains valuable, but its role changes:

- bootstrap `lns.json`
- validate existing repo config
- produce actionable unresolved errors

Autodetection must not silently decide production routing behavior in steady state. Once `lns.json` exists, `lns sync` should compile from that file, not from best-effort guesses.

Detection decisions:

- `lns init` may generate or fill an initial `lns.json`.
- `lns sync` may validate against codebase evidence and report drift.
- `lns sync` must not repair config automatically.
- Ambiguous detection should emit unresolved stubs with exact missing fields.

### Fallback Policy

Remove these behaviors from the canonical workflow:

- falling back to `generic`
- falling back to `9000-9099`
- framework-range assignment as the primary behavior

Preferred error model:

- if `lns.json` is missing, `lns init` creates it
- if a service is incomplete, `lns sync` reports `unresolved`
- if the configured port appears inconsistent with codebase signals, `lns status` or `lns sync` reports drift explicitly

Port conflict decision:

- If one repo's canonical `port` conflicts with another repo's canonical `port`, `lns sync` should hard-fail with a clear ownership error.
- No automatic port reassignment should occur.
- If a user wants a different port locally, they should change `lns.json` or use `lns service add` explicitly.

Hostname decision:

- Default hostnames remain derived from `<project-prefix>.localhost` for single-service repos and `<project-prefix>-<service-name>.localhost` for multi-service repos.
- `hostname` remains optional explicit config in `lns.json`.
- Hostname conflicts should block sync just like port conflicts.

## Technical Approach

### Phase 1: Introduce the New Canonical Data Model

Target files:

- `internal/models/models.go`
- `internal/registry/registry.go`

Tasks:

- Replace `Framework` and `FrameworkInfo` as the center of the service model.
- Add a smaller proxy-oriented type for `profile`.
- Extend `Service` to store `Root`, `Profile`, `Source`, and `Status`.
- Simplify `Registry` so it stores resolved service definitions rather than framework-derived allocation state.
- Remove framework-range logic from the core model.
- Define `ProfileHMR` and `ProfileStandard` as the initial supported profiles.

Success criteria:

- Service definitions can be represented without framework metadata.
- The model can distinguish canonical config from detected suggestions.

### Phase 2: Add Canonical Repo Config Support

Target files:

- new `internal/projectconfig/...`
- `cmd/lns/main.go`

Tasks:

- Add load/save helpers for `lns.json`.
- Define validation rules for required service keys.
- Make `lns init` write `lns.json` when absent.
- Make `lns service add` edit `lns.json` instead of directly mutating service state only in the global registry.
- Add a stub-writer for unresolved services so ambiguous repos still get a usable manifest.

Success criteria:

- `lns.json` is the canonical per-repo contract.
- Manual service definition updates repo config, not just global state.

### Phase 3: Re-scope Discovery to Bootstrap and Validation

Target files:

- `internal/discovery/discovery.go`
- `internal/discovery/discovery_test.go`

Tasks:

- Split discovery into:
  - root discovery
  - service detection
  - port detection
  - profile detection
  - drift reporting
- Remove framework fallback behavior from discovery output.
- Make detection return evidence and confidence instead of implicit defaults.
- Add unresolved outcomes when detection cannot determine required data.
- Add deterministic `profile` inference rules:
  - HMR for Vite, Next.js, Nuxt, Vue CLI, and CRA style dev servers
  - standard for backend HTTP servers unless explicitly configured otherwise

Success criteria:

- Discovery can generate a first-pass `lns.json`.
- Discovery does not silently assign generic fallback values.

### Phase 4: Rewrite Sync as Deterministic Compilation

Target files:

- `cmd/lns/main.go`
- `internal/registry/registry.go`
- `internal/caddy/caddy.go`

Tasks:

- Add `lns sync` as the primary compile step.
- Read `lns.json`, validate it, update registry state, and regenerate Caddy config.
- Make Caddy generation depend on `profile` and `port`, not `framework`.
- Ensure unresolved services block sync with actionable errors.
- Make sync transactional at the application level:
  - validate all services first
  - only then rewrite registry and generated config
  - leave prior generated output untouched on failure

Success criteria:

- A repo with a valid `lns.json` can be synced without any framework flags.
- Caddy config is derived from canonical repo config.

### Phase 5: Redesign the Command Surface

Target files:

- `cmd/lns/main.go`
- `README.md`

Tasks:

- Make `init` and `sync` the documented happy path.
- Add `service add` for explicit manual configuration.
- Remove `add` and `suggest`, and demote `check` from the primary UX.
- Update help text, examples, and README to reflect repo-first configuration.
- Add `status` output that distinguishes:
  - resolved services from config
  - unresolved services
  - drift between config and detected codebase signals

Success criteria:

- The top-level docs show a repo-first workflow.
- Users do not need to think about frameworks during normal setup.

### Phase 6: Remove Compatibility and Dead Paths

Target files:

- `internal/models/models.go`
- `internal/registry/registry.go`
- `cmd/lns/main.go`
- `README.md`

Tasks:

- Remove old framework-first paths instead of keeping adapters.
- Delete generic fallback behavior.
- Delete deprecated registry behavior that only exists for old commands.
- Update examples to use `lns.json`, `init`, and `sync`.
- Delete any parser or loader code that accepts old registry-era service semantics.

Success criteria:

- The codebase has a single coherent model.
- No compatibility shims remain.

## Alternative Approaches Considered

### Keep Frameworks and Improve Detection Incrementally

Rejected because:

- it preserves the wrong abstraction
- it keeps fallback complexity alive
- it still makes the registry the real source of truth

### Make Runtime Port Assignment the Primary Model

Rejected as the core design because:

- Caddy config still needs a deterministic resolved state before reload
- the user explicitly wants `lns sync` to define service bindings from repo state
- runtime assignment only makes sense as a separate future process-supervision mode, not the base architecture

## System-Wide Impact

### Interaction Graph

- `lns init` will scan repo files and produce `lns.json`.
- `lns sync` will read `lns.json`, run validation, update the registry, regenerate Caddy files, and require `lns reload` or an integrated reload step.
- Caddy generation will consume resolved service definitions rather than framework metadata.

### Error & Failure Propagation

- Invalid `lns.json` should fail before registry mutation.
- Unresolved services should fail before Caddy generation.
- Caddy write failures should not leave registry and generated config silently diverged.
- Sync should either complete fully or stop with a precise error message and no partially-updated compile step.
- Port and hostname conflicts should fail before any output is rewritten.

### State Lifecycle Risks

- Registry rewrite must avoid orphaning stale service entries when names or roots change.
- If sync removes services, project Caddyfiles must be regenerated in the same operation.
- Dirty working-tree autodetection code may conflict with the new model if reused without narrowing its role.

### API Surface Parity

The following interfaces need aligned redesign:

- CLI commands in `cmd/lns/main.go`
- repo-local config loading
- registry persistence
- Caddy generation
- docs/examples in `README.md`
- repo-local `lns.json` contract

### Integration Test Scenarios

- `lns init` on a single-app Vite repo writes a correct `lns.json`.
- `lns init` on a monorepo creates multi-service or unresolved stubs correctly.
- `lns sync` fails on unresolved service definitions without mutating Caddy output.
- `lns sync` regenerates project and global Caddyfiles from canonical config.
- `lns service add web --port 5179` updates canonical repo config and then sync compiles correctly.
- `lns sync` fails when another repo already owns the same canonical port.
- `lns sync` fails when two services resolve to the same hostname.
- `lns status` reports drift when repo code indicates a different port or profile than `lns.json`.

## Acceptance Criteria

### Functional Requirements

- [x] `lns.json` exists as the canonical repo config format.
- [x] `lns init` can generate `lns.json` from common repo structures.
- [x] `lns sync` compiles canonical repo config into registry and Caddy state.
- [x] `lns service add <name> --port <port>` exists for explicit manual configuration.
- [x] Service proxy behavior is expressed via `profile`, not required framework flags.
- [x] No silent `generic` or `9000` fallback remains in the main workflow.
- [x] `lns sync` does not mutate `lns.json`.
- [x] Port conflicts and hostname conflicts hard-fail with exact ownership messages.

### Non-Functional Requirements

- [x] Sync output is deterministic for the same repo state.
- [x] Validation errors name the exact unresolved service and missing field.
- [x] Dirty global state is not required to understand a repo's configuration.

### Quality Gates

- [x] Unit tests cover discovery bootstrap, config parsing, sync compilation, and Caddy generation.
- [x] README examples reflect the new workflow only.
- [x] Removed legacy code paths are not kept behind flags.

## Success Metrics

- New project setup requires no framework flag in the normal path.
- The primary setup flow becomes `lns init` + `lns sync`.
- Port-related support issues caused by silent fallback behavior drop to zero.
- The mental model of "repo config defines reality" is consistent across docs and implementation.

## Dependencies & Risks

Dependencies:

- A stable `lns.json` schema decision
- Agreement on `profile` values and required service fields
- Command-surface cleanup in Cobra

Risks:

- The existing autodetection work may tempt incremental reuse beyond its intended role.
- Breaking the old registry format without removing all old assumptions can leave hybrid logic behind.
- Repo scanning can still be ambiguous in monorepos; unresolved-state UX must be strong enough to be useful.

## Canonical Schema Proposal

Initial `lns.json` schema for implementation:

```json
{
  "name": "heyjustin",
  "prefix": "heyjustin",
  "services": {
    "web": {
      "root": ".",
      "port": 5179,
      "profile": "hmr",
      "hostname": "heyjustin.localhost"
    }
  }
}
```

Required top-level fields:

- `name`
- `services`

Required service fields:

- `root`
- `port`
- `profile`

Optional service fields:

- `hostname`

## SpecFlow Analysis Summary

User-flow and gap analysis surfaced these decisions, which are incorporated into this plan:

- Port conflicts are blocking errors, not candidates for silent reassignment.
- `lns.json` is required after bootstrap and remains canonical.
- `lns sync` is a read/validate/compile step, not a repair step.
- Service identity in monorepos comes from manifest keys.
- Manual services and detected services must share one manifest model.
- Sync should be all-or-nothing rather than partially compiling valid services.

## Implementation Order

1. Redefine models in `internal/models/models.go`.
2. Add `lns.json` loader/writer and validation.
3. Rework discovery around bootstrap and drift reporting only.
4. Add `lns sync` and make it transactional.
5. Update Caddy generation to consume `profile` and `port`.
6. Add `lns service add` manifest editing.
7. Remove framework-first and fallback-era commands and docs.
